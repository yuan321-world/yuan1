# 需求与开发流程补充

日期：2026-10-14。此文补齐协作流程，不增加产品范围或调整原阶段顺序。

## 首版目标与角色

首版暂以大学生四级英语学习和阅读训练为主，目标人群尚属方案假设。V1 内测版在阶段 4 交付：登录 → 阅读 → 查词 → 收藏带来源的生词 → 复习 → 阅读题答题 → 解析及错题重做。

| 角色 | 首版职责 | 实施位置 |
| --- | --- | --- |
| 学习者 | 使用自己的收藏、学习记录与练习记录 | 阶段 1—4 |
| 管理员 | 维护文章、词书、题组，执行预览、发布、下架与内容校验 | 随对应业务阶段完成最小后台 |
| 未登录用户 | 阶段 0 仅查看工程布局；正式学习访问边界随阶段 1 设计 | 不将原型的访问行为视为正式权限规则 |

管理员账号维护在阶段 1 详细设计中明确；不增加复杂用户运营后台。AI、留言墙、多考试仍按原阶段 6 规划，Redis、Python 和容器工具的引入时机不变。

## 用户故事与验收关联

| 用户想完成的事 | 可观察结果 | 阶段 |
| --- | --- | --- |
| 登录后继续学习 | 会话有效且不能读取他人记录 | 1 |
| 查阅文章中的生词 | 词义清楚，收藏保留原句与来源，刷新不丢失 | 2 |
| 知道今天复习什么 | 到期词来自真实记录，反馈改变下一次安排 | 3 |
| 用阅读题检验理解 | 作答恢复、交卷结果一致、解析和错题重做可用 | 4 |
| 管理员添加下一批内容 | 无需修改代码，内容先校验再发布 | 对应阶段 |

每个阶段设计以这些用户行为为依据，继续使用原方案的数量、内容和异常场景要求；不因补充流程而承诺新的功能。

## 每阶段开工前的设计审查

在该阶段实现前，检查同一条用户流程的四份信息是否一致：需求、页面状态、数据库与接口。只细化当前阶段，后续业务表不提前定死。

审查记录至少包含：范围与非目标；角色和资源归属；UI 加载/成功/空数据/失败/中断状态；数据字段、关系、索引、唯一性及迁移；请求、响应、错误和权限；依赖阶段；自动验证和人工验收方法；仍未决定的事项及负责人。

存在明确的接口或数据矛盾时先修设计。已经获得授权的常规实现和验证继续执行；只有缺少必要业务信息、跨越原范围或涉及新的外部动作时再提出具体问题。参考文件里的示例确认流程不覆盖本会话已经提供的授权。

## 单任务交付顺序

检查当前工作 → 核对本阶段 UI/数据/API → 编写必要测试及实现 → 前后端联调 → 检查差异 → 更新文档 → 提交本任务文件 → 更新进度。

代码审查重点：是否满足用户行为、接口是否一致、是否发生越权或重复写入、迁移是否影响历史记录、错误是否可恢复、是否引入无关框架、是否包含凭据或演示脚本。独立审查按已经选定的协作方式执行，不默认为每个小任务创建新代理。

## 任务与会话交接模板

```text
当前阶段 / 任务：
本次要交付的用户行为：
必须阅读的方案、计划、UI、数据库、API：
消费和产生的接口 / 数据：
允许修改的文件与范围：
必要测试与期望结果：
实际修改：
实际验证：命令、退出码、真实/Mock、未执行项目
未解决问题与下一步：
```

不向任务加入“开发整个网站”这类无边界目标。新会话依据 progress.md 和验收证据继续，不能看到已有代码就认定阶段完成。

## 对外交付检查

沿用阶段 4 对外上线前的要求：账号恢复、HTTPS、访问控制、限流及备份恢复。进一步明确部署验收应记录：配置与密钥来源、数据库迁移步骤、启动/健康检查、history 路由回退、持久化卷、备份恢复实测和应用回滚方法。

应用回滚与数据库回滚分开规划：优先兼容迁移，不自动用旧代码回滚破坏性数据变更。使用测试环境先验证，再按用户决定发布。

性能检查只针对实际负载制定：记录数据规模、并发量、响应耗时、慢查询和错误率；出现慢查询再检查索引与分页，出现第三方超时则验证有界超时和降级。尚未确定的上线负载不伪造响应指标，也不因此提前引入微服务、Redis 或更多基础设施。
